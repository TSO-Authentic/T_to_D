# PART A — WHY ARE WE HERE?

## Slide 1 — Software Development Is Changing

### Main Content

Software development has always evolved with better tools:

```text
Text Editor
    ↓
IDE
    ↓
Code Completion
    ↓
AI Chat
    ↓
AI-Assisted Editing
    ↓
AI Planning
    ↓
AI Agents
    ↓
Agentic Software Development
```

The major change is not simply:

> "AI can write code."

The bigger change is:

> **AI can increasingly participate in the software development process itself.**

### Key Explanation

Traditional AI coding tools primarily help developers perform individual activities.

Modern coding agents can perform a sequence of activities:

* Understand a goal
* Explore a repository
* Reason about the implementation
* Modify multiple files
* Run tools
* Execute tests
* Analyze failures
* Iterate
* Report the result

### Takeaway

**The unit of AI assistance is moving from a line of code toward an engineering task.**

> **Understanding → Deciding → Executing → Verifying**

## Slide 4 — Agentic Software Development

### Main Content

An AI agent receives a **goal**, not necessarily a detailed sequence of instructions.

```text
Developer
    │
    │ Goal + Constraints
    ↓
   Agent
    │
    ├── Understand
    ├── Explore
    ├── Plan
    ├── Modify
    ├── Test
    ├── Analyze
    └── Iterate
```

### Example

Instead of:

> "Create a validation method."

The developer can ask:

> "Add validation for user registration, follow the existing validation pattern, add regression tests, run the relevant tests, and fix any failures."

The agent may determine the intermediate steps.

### Key Idea

**Agentic development is goal-oriented and multi-step.**

---

## Slide 5 — What Makes a Workflow "Agentic"?

### Main Content

A workflow becomes increasingly agentic when AI can:

1. Understand a goal
2. Access relevant context
3. Decide intermediate actions
4. Use tools
5. Change the environment
6. Observe results
7. React to feedback
8. Iterate toward completion

### Agentic Characteristics

```text
Goal
 ↓
Reasoning
 ↓
Action
 ↓
Observation
 ↓
Feedback
 ↓
Iteration
```

### Important Distinction

Generating code once is not necessarily agentic.

An agentic workflow looks more like:

> **Generate → Execute → Observe → Adapt → Verify**

## Slide 6 — Traditional vs AI-Assisted vs Agentic

### Main Content

| Capability                 | Traditional  | AI-Assisted  | Agentic           |
| -------------------------- | ------------ | ------------ | ----------------- |
| Human writes code          | High         | High/Medium  | Medium/Low        |
| AI generates code          | No           | Yes          | Yes               |
| AI explains code           | No           | Yes          | Yes               |
| AI understands repository  | Human-driven | Partial      | Stronger          |
| AI uses tools              | No           | Limited      | Yes               |
| AI modifies multiple files | Human        | Sometimes    | Common            |
| AI runs tests              | Human        | Sometimes    | Often             |
| AI reacts to failures      | Human        | Mostly human | Agent can iterate |
| Autonomy                   | Low          | Low/Medium   | Medium/High       |

### Takeaway

> **AI-assisted development helps the developer perform a task.**

> **Agentic development allows AI to perform parts of the task.**

## Slide 10 — Code Completion

### Main Content

### What is it?

AI predicts or generates code while the developer is writing.

### Best for

* Small functions
* Boilerplate
* Repetitive code
* Simple transformations
* Test skeletons
* Common programming patterns

### Example

```text
Developer:

function calculateTotal(items) {

    // AI suggests implementation
}
```

### Mental Model

> **AI as intelligent autocomplete**

### Limitations

Code completion is usually not the right tool for:

* Large architectural changes
* Repository-wide changes
* Complex debugging
* Multi-step workflows

## Slide 11 — Ask / Chat

### Main Content

### Purpose

Ask is primarily for:

> **Understanding, investigation, explanation, and discussion.**

### Examples

```text
Explain this authentication flow.

Why is this function returning null?

Where is user validation implemented?

What happens when this API receives an invalid request?
```

### Mental Model

> **AI as a technical consultant**

### Typical Workflow

```text

   ↓

   ↓
```

The important point is that the interaction is primarily informational.

## Slide 12 — Ask: When Should I Use It?

### Use Ask When:

* You don't understand existing code
* You need to investigate behavior
* You want architectural explanations
* You want alternatives
* You need help debugging
* You want to understand dependencies
* You want to ask "why?"

### Example

> "Why does submitting an empty username result in HTTP 500?"

The AI can investigate:

```text
Controller
   ↓
Validation
   ↓
Service
   ↓
Exception
   ↓
Error Handler
```

### Key Idea

Ask is excellent for **reducing uncertainty before acting**.

## Slide 13 — Plan

### Main Content

### What is a Plan?

A Plan is an implementation-oriented analysis of:

> **What needs to change, where it needs to change, and how the change should be approached.**

Example:

```text
Requirement:
Add wishlist functionality.

Plan:
1. Identify current user model
2. Identify product ownership
3. Determine persistence pattern
4. Add wishlist model
5. Add repository/data access
6. Add service logic
7. Add API endpoints
8. Add validation
9. Add tests
10. Run verification
```

### Key Idea

A plan converts:

> **Requirement → Implementation strategy**

* Helps estimate scope
* Makes complex tasks easier to control

## Slide 16 — Can Plan Inspect the Existing Codebase?

### Main Content

Yes, when the relevant Copilot environment provides repository/file context and tools.

A plan can investigate:

* Existing classes/components
* Existing patterns
* Dependencies
* Configuration
* Tests
* APIs
* Similar implementations
* Project conventions

### Example

Requirement:

> "Add two-factor authentication."

The agent should first discover:

```text
Current authentication
       ↓
User model
       ↓
Session/token handling
       ↓

       ↓
```

### Key Idea

Planning should be **repository-aware**, not just generic advice.

## Slide 17 — What Does a Good AI-Generated Plan Look Like?

### Main Content

A strong plan should identify:

### 1. Goal

What are we trying to achieve?

### 2. Existing architecture

How does the current system work?

### 3. Affected components

Which modules/files/components are likely to change?

### 4. Implementation steps

What should happen and in what order?

### 5. Testing strategy

How will we verify the change?

### 6. Risks

What existing behavior could be affected?

### 7. Assumptions

What does the plan assume?

### Good Plan

> "Modify the existing authentication flow while preserving the current authorization mechanism."

### Weak Plan

> "Add authentication files and update the application."

---

## Slide 18 — Limitations of AI-Generated Plans

### Main Content

A plan is **not automatically a correct architecture decision**.

Potential problems:

* Incorrect assumptions
* Missing hidden dependencies
* Misunderstanding business rules
* Incomplete repository context
* Wrong interpretation of existing architecture
* Overengineering
* Missing edge cases

### Therefore

```text
AI Plan
   ↓
Human Review
   ↓
Approved Approach
   ↓
Implementation
```

### Key Principle

> **A plan is a decision-support artifact, not a replacement for engineering judgment.**

## Slide 28 — Instructions

### Main Content

Instructions are persistent rules or guidance that tell Copilot how to work.

Examples:

```text
Follow the existing architecture.

Use the existing error-handling pattern.

Always write tests for new business logic.

Do not introduce new dependencies without justification.

Do not modify production configuration unless explicitly requested.
```

GitHub currently supports several instruction scopes, including repository-wide and path-specific instructions, with support varying by Copilot surface.

## Slide 29 — Why Instructions Matter

### Without Instructions

```text
Agent
   ↓
Generic solution
```

### With Instructions

```text
Agent
   ↓
Project conventions
   ↓
Project-specific solution
```

### Instructions can encode

* Coding conventions
* Architecture rules
* Testing standards
* Build commands
* Deployment restrictions
* Security requirements
* Naming conventions
* Framework preferences

### Key Principle

> **Instructions turn generic AI behavior into project-aware behavior.**

## Slide 30 — Prompt vs Instruction

### Main Content

| Prompt                 | Instruction                               |
| ---------------------- | ----------------------------------------- |
| Usually task-specific  | Usually persistent                        |
| "Implement login"      | "Use the existing authentication pattern" |
| Describes current task | Defines working rules                     |
| User provides it       | Team/project can provide it               |
| Temporary              | Reusable                                  |

### Simple Mental Model

> **Prompt = What do I want now?**

> **Instruction = How should you work in this environment?**

## Slide 31 — Example: Project Instructions

### Main Content

Imagine a repository contains:

```text
.github/
    copilot-instructions.md
```

Instructions:

```text
- Follow the existing layered architecture.
- Prefer constructor injection.
- Do not introduce Lombok.
- Use the existing logging framework.
- Write unit tests for business logic.
- Use the project's existing test framework.
- Do not modify database migration files unless explicitly requested.
- Run the standard test command before considering implementation complete.
```

### Result

When an agent works on the project, these rules can guide its implementation.

### Important

Instructions do not make the agent infallible.

They **constrain and guide behavior**.

## Slide 32 — Good vs Bad Instructions

### Good

> "Use the existing error-handling mechanism instead of creating a new global exception framework."

Why?

* Specific
* Actionable
* Project-oriented

### Bad

> "Write good code."

Why?

* Ambiguous
* Difficult to verify
* No concrete behavior

### Good

> "For business logic changes, add or update unit tests using the project's existing test framework."

### Bad

> "Always make everything fully tested."

## Slide 39 — Instruction vs Skill vs Agent

### Main Content

This distinction is essential.

```text
Instruction
"What rules should I follow?"

Skill
"How should this particular task be performed?"

Agent
"What role am I performing and what responsibilities do I have?"
```

### Example

```text

Use the existing testing framework.

Skill:

Testing Agent:
Specialist responsible for software testing.
```

GitHub recommends using simple, broadly applicable rules as custom instructions and more detailed task-specific procedures as skills.

## Slide 46 — A Formula for Agent Prompts

### Main Content

A useful agent prompt can contain:

```text
GOAL
What should be achieved?

What should the agent understand?

What should it change?

CONSTRAINTS
What must it avoid?

What should it investigate or verify?

What should it report?
```

### Example

> Implement the requested feature.
